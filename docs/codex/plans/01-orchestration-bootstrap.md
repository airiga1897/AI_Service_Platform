# Step-by-step: control/orchestration bootstrap

## Current Bootstrap/Re-Bootstrap Model

Current bootstrap behavior is role-aware and supports both fresh VPS setup and
re-bootstrap of already prepared nodes:

- A non-empty `root_password` in `operator/nodes.csv` means fresh bootstrap
  through `root@host`.
- An empty `root_password` means admin-key re-bootstrap through
  `useradmin@host` with `operator/<alias>/admin_key`.
- `platform_role,orchestration` `active_aliases` and `candidate_aliases` are
  treated as management-capable nodes.
- Other `present` aliases are treated as managed nodes.
- `bootstrap_all_from_windows.ps1` automatically converges existing
  present/candidate nodes when their admin keys exist.
- The Windows wrapper prepares standby trust in one pass: candidate keys,
  aggregate Ansible trust bundle, orchestration trust mesh, then managed-node
  re-bootstrap.

Admin-key re-bootstrap runs a preflight before changing the target. It verifies
SSH access, passwordless sudo, `/tmp` write access, baseline commands, Ubuntu
apt support, and management-package installability where relevant. If those
checks fail, fix the reported prerequisite or run a fresh root-password
bootstrap after reinstalling the OS.

Remote keys are not regenerated by default. Regeneration remains explicit and
requires force for management-capable nodes.

Этот документ описывает первый инфраструктурный шаг: подготовить VPS после fresh OS install, выбрать active orchestration node из `state.csv`, синхронизировать operator-файлы, создать `inventory.ini` и выполнить verify.

`vps1`, `vps2`, `vps3` - это operator aliases. Реальный управляющий узел выбирается не по имени `vps3`, а по строке `platform_role,orchestration` в `operator/state.csv`.

## 1. Operator files

На операторской машине должны быть ignored-файлы:

```text
operator/nodes.csv
operator/state.csv
```

`operator/nodes.csv` - только адресная книга и временный root password для первого bootstrap:

```csv
current_alias,endpoint,expected_ip,connection,ssh_port,root_password
vps1,vps01.example.com,ssh,<temporary-root-password>
vps2,vps02.example.com,ssh,<temporary-root-password>
vps3,vps03.example.com,ssh,<temporary-root-password>
```

`operator/state.csv` - желаемая картина ролей и сервисов:

```csv
kind,name,ansible_group,active_aliases,candidate_aliases,old_aliases,state
platform_role,orchestration,orchestration,vps3,,,present
platform_role,monitoring,monitoring,vps3,,,present
platform_role,backup,backup,vps2,,,present
service,edge_haproxy,edge_haproxy,vps1,,,present
service,vpn_edge,vpn_edges,vps1+vps2+vps3,,,present
service,vpn_cascade,vpn_cascades,,,,absent
```

`state=present/absent/purged` само по себе ничего не запускает. Запуск делает только явная команда runner-а.

## 2. Bootstrap pending VPS

Основной запуск с Windows один и тот же для fresh bootstrap, добавления нового
VPS и переустановки отдельного VPS:

```powershell
.\tools\bootstrap\bootstrap_all_from_windows.ps1 -AutoAcceptHostKey
```

Wrapper делает полный цикл по `nodes.csv` и `state.csv`:

1. Находит active orchestration node по `platform_role,orchestration`.
2. Считает pending только те VPS, у которых в `operator/nodes.csv` заполнен
   временный `root_password`.
3. Если active orchestration node pending, bootstrap-ит его первым.
4. Если active orchestration node уже без `root_password`, использует
   существующий `operator/<orchestration-alias>/admin_key` и не трогает его
   через root bootstrap.
5. Сохраняет Ansible public key в `operator/ansible_control.managed_nodes.pub`.
6. Сохраняет keys узла в `operator/<alias>/`.
7. Bootstrap-ит остальные pending VPS как managed nodes.
8. Очищает `root_password` в `operator/nodes.csv` только после успешного
   bootstrap соответствующего alias.
9. Выполняет sync на orchestration node.
10. Готовит `/opt/ai-service-platform/inventory.ini`.
11. Запускает verify и service plan.

Для добавления нового VPS достаточно добавить строку с новым alias и временным
`root_password`, например:

```csv
vps4,vps04.example.com,ssh,<temporary-root-password>
```

Затем запустить тот же `bootstrap_all_from_windows.ps1`. Wrapper увидит, что
pending только `vps4`, bootstrap-ит только его, очистит пароль и выполнит
sync/verify.

Если в команде остался `-ForceManagementKeyRefresh`, но active orchestration
node не pending, wrapper использует существующий Ansible control key и выводит
warning вместо повторного root bootstrap управляющего узла.

Стандартные пути `.\operator\nodes.csv`, `.\operator\state.csv` и
`.\operator\ansible_control.managed_nodes.pub` используются автоматически.
Параметры `-NodesFile`, `-StateFile`, `-OperatorDir` и
`-AnsibleAuthorizedKeyFile` нужны только для advanced/debug override.

## 3. Sync на orchestration node

Основная команда sync:

```powershell
.\tools\bootstrap\sync_to_orchestration.ps1 -AutoAcceptHostKey
```

Основной sync entrypoint теперь только `sync_to_orchestration.ps1`/`.sh`; orchestration alias выбирается из `state.csv`.

Sync всегда отправляет на orchestration node sanitized `nodes.csv` без root passwords.

Для уменьшения шума в логах Windows runner отправляет service/operator bundles одним `tar.gz` и распаковывает их на orchestration node. POSIX sync использует `rsync --delete`, если `rsync` доступен локально и на orchestration node; иначе остаётся `scp` fallback.

Для первичного bootstrap orchestration row должна быть `present`, например:

```csv
platform_role,orchestration,orchestration,vps3,,,present
```

`absent` для `orchestration` не используется как стартовое состояние: без active orchestration node wrapper не сможет выбрать первый control VPS. Для будущего переноса сначала используется candidate:

```csv
platform_role,orchestration,orchestration,vps3,vps4,,present
```

После проверки новый узел становится active, а старый временно остаётся в `old_aliases`:

```csv
platform_role,orchestration,orchestration,vps4,,vps3,present
```

## 4. Automatic verify

Verify выполняет:

```bash
sudo -u ansible ansible all -i /opt/ai-service-platform/inventory.ini -m ping
sudo -u ansible ansible all -i /opt/ai-service-platform/inventory.ini --become -m shell -a 'sshd -T ...'
```

Ожидаемый hardening на каждом узле:

```text
permitrootlogin no
passwordauthentication no
```

Успешный bootstrap/sync означает: inventory создан, Ansible ping прошёл, root/password SSH login выключен.

## 5. Service rollout после bootstrap

После успешной инфраструктурной подготовки обычный operator flow:

```powershell
.\tools\services\rollout_from_state.ps1 `
  -NodesFile .\operator\nodes.csv `
  -StateFile .\operator\state.csv
```

Скрипт сам делает sync + verify, читает все `kind=service` из `state.csv` и применяет поддержанные сервисы. GitHub Actions пока не участвуют.

## 6. Reinstall одного VPS

Если переустановлен managed VPS:

1. В `operator/nodes.csv` добавь временный `root_password` только для этого alias.
2. Запусти обычный pending bootstrap:

   ```powershell
   .\tools\bootstrap\bootstrap_all_from_windows.ps1 -AutoAcceptHostKey
   ```

3. Wrapper сам выполнит sync, inventory и verify после успешного bootstrap.

Низкоуровневый `bootstrap_from_windows.ps1 -Alias <alias>` оставлен для
ручной диагностики и аварийных случаев, но не является обычным operator flow.
Он тоже использует standard operator layout автоматически:

```powershell
.\tools\bootstrap\bootstrap_from_windows.ps1 -Alias vps4 -AutoAcceptHostKey
```

Если переустановлен active orchestration node, его Ansible control key считается новым. Managed nodes нужно заново bootstrap-нуть или отдельно доставить новый public key.
